## 3. Scientific and public API contracts

Adopt TWO distinct, model-specific public operations with well-defined input/output types and ps2_ public symbols. Names in the D1 plan are design intent, so use concrete consistent C identifiers, documenting exact signatures and field ownership:

  ps2_beta_update(prior, events, nonevents, out)
  ps2_beta_predict(posterior, future_n, wanted_k, out)

New header: models/include/probspan_models/beta_predict.h (or an equally narrow source-backed header). Implementation: models/src/beta_predict.c plus narrowly justified private helpers. Include C++ linkage guards and C11 fixed-width integers. Keep Models ABI generation 1 and the existing F001 public header unchanged.

**Prior/update semantics**

- Caller specifies Beta(a0,b0) with two finite positive binary64 shape parameters, each within [0.5, 1,000,000] inclusive.
- events and nonevents are nonnegative uint64_t counts. Prevent integer overflow. Their sum must be at most 1,000,000; otherwise return UNSUPPORTED with documented validation precedence.
- Observations are homogeneous, disjoint, fixed binary event definitions, same time horizon, independent conditional on a common p. The caller warrants evidence admission; the library cannot prove that.
- Posterior shapes: a=a0+events, b=b0+nonevents. Predictive probability for one future homogeneous Bernoulli unit: m=a/(a+b). Preserve the explicit input prior, the evidence counts and posterior shapes in a typed result if practical to support reproducible source semantics.
- With no observations (0,0), return a valid, expressly marked prior-only result with posterior equal to prior; do NOT report empirical target evidence or apply v1 readiness gate. Example: Beta(1,1), 1 event, 2 nonevents => Beta(2,3), m=0.4.
- Do not label an arbitrary explicit prior as validated or automatically "robust". Do not admit historical results or prior from unrelated populations automatically.

**Prediction semantics**

- Accept only validated posterior shapes resulting from the declared F002 shape/update domain; do not trust an arbitrary caller-mutated struct without validation. Document version/validity semantics and how a caller can intentionally construct a supported posterior, if permitted.
- future_n is uint64_t in [0, 10,000], wanted_k in [0, future_n]. Count overflow/invalid arguments must be rejected before conversion to C indices.
- For N future conditional exchangeable Bernoulli trials integrated over Beta(a,b):

  P(K=k | a,b,N) = choose(N,k) * B(a+k,b+N-k) / B(a,b).

- Also return log PMF, expected count E[K]=N*m, variance Var[K]=N*m(1-m)*(a+b+N)/(a+b+1). In particular, variance for N>1 is generally greater than simple plug-in binomial variance. Compare independent tests for exact N=1 behavior and the N=0 corner.
- N=0 and k=0 yield PMF exactly 1, log PMF exactly 0, mean=0 and variance=0; this is a supported success, not an EMPTY failure.
- Valid shapes and in-support k imply mathematically strictly positive PMF. Distinguish (a) structural true zero (not present in this positive-shape valid-support model, except explicitly defined out-of-support diagnostic cases), (b) nonzero mathematical mass rounding/underflowing to +0, and (c) nonzero but representably lossy binary64 value. Return finite log PMF when real PMF is too small to encode, and a clear result diagnostic. Never silently treat zero encoded PMF as impossible event, or replace infinity with a normal finite log probability.
- Do not silently clip, normalize, rescale probability support, or reinterpret the posterior as a new Jeffreys gate. Define whether log PMF and PMF are computed directly/recursively and how normalization is established.
- Input ownership stays with caller; no output/input aliasing. No clock, RNG, I/O, hidden mutable global state or heap allocation in the runtime C11 package. Prefer O(1) workspace, O(N) bounded prediction work where stable recurrence requires it.
- Errors must distinguish INVALID_ARGUMENT, UNSUPPORTED, NUMERICAL_FAILURE, and if appropriate EMPTY only for genuinely absent required data; prior-only and N=0 prediction are successful, not empty. Validation precedence must be documented and tested. ALL failures leave output bytes unchanged; calculate into local temporary and publish only on success.
- Successful numeric outputs must be finite wherever mathematically finite, with explicitly diagnosed representability loss. Add clear checks for NaN, infinity, invalid negative or oversized shapes, corrupted or uninitialized result objects, large uint64_t values, and unexpected numerical state. Avoid integer overflow and undefined behavior.

## 4. Numerical implementation choices and solver boundary

Prefer a stable, independently auditable Beta-Binomial mass recurrence. A defensible implementation can use:

  P(K=k+1)/P(K=k) = ((N-k)/(k+1)) * ((a+k)/(b+N-k-1)).

Use appropriate direction or mode anchoring and scale/normalization to prevent overflow or underflow and catastrophic cancellation. A straightforward signed log-recurrence or scaled-mass log-sum-exp approach may be acceptable when accompanied by a justified finite-domain numerical budget. Do not assume repeated lgamma subtraction remains accurate for a,b near 10^6; compare against independent high-precision log Beta and a separately computed recurrence. For performance, use bounded loops with deterministic maximum work; no unbounded search or recursive stack use. Keep the normalizer and requested tail mass distinct. Verify that normalized mass values across N+1 support agree with independent references within the approved budget, and that the mean/variance formulas preserve their intended model semantics.

Actual solver and public output type design are engineering details, but must remain within the approved F002 domain and preserve public contract meaning. Do not copy old private Beta, gamma or quantile solvers, couple to F001's CP internal arithmetic, or add SciPy/NumPy/Python to installed runtime. C standard math/libm linkage is permitted and must be propagated correctly in exported CMake metadata.

The numerical policy is based on exact encoded binary64 input values and integer counts, not decimal expressions assumed exact after source conversion. Follow normal binary64/rounding/gradual-underflow environment requirements. A numerical failure must not be falsely relabeled INVALID_ARGUMENT just to pass.
